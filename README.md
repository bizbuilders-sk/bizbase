# BizBase

BizBuilders workspace for presales, accounts and contacts, delivery projects, service revenue, and external vendor costs. React, TypeScript and Vite on Cloudflare Pages, backed by Supabase Auth and Postgres.

## Run

Use Node 22.18+ (or Node 24+) for the test suite.

```sh
npm install
npm run dev
npm test
npm run build
```

The app includes the public configuration for the BizBase Supabase project. Staff still need to sign in and have active workspace membership. Optional `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` overrides can target a different environment. Never use a secret or service-role key in frontend configuration.

## Current UI

- **Deals:** Deal pipeline; the former Lead intake tab is removed. Open deals are the default opportunity filter; won, lost and all-record views are available. Sales owner selects a named directory entry. Proposed service lines use the same catalog as delivery. Stage changes apply the configured probabilities (35, 37, 38, 50 and 52 percent; won 100, lost 0). Lost transitions capture a reason. Values and weighted forecast remain separate.
- **Enquiries:** Contact and Company cards no longer have an Enquiries tab (4 Nov 2026); nearly all enquiries duplicate a submission in the **Webform submissions** tab (formerly Event history), which holds event registrations and standalone contact-form messages. The standalone intake tab and its old qualification action are removed; no source records or enquiry history are deleted, and an event registration card can still open its linked enquiry. Automatic webform routing remains a separate integration. Company Lead status and Won-to-Project automation are enforced in the database (see below).
- **Projects:** Delivery phase, client, group, contract value, dates and owner. Record tabs expose services, monthly revenue allocations, vendor costs, notes and original imported fields. Creating a delivery project from an opportunity marks that opportunity won in the same transaction. Optional proportional allocation includes both delivery endpoint months and reconciles to the cent.
- **Revenue plan:** Contract value, delivery dates and monthly allocations save together. A plan must equal the contract value, use unique valid months and contain nonnegative EUR amounts. Existing manual allocations are replaced only when the user saves the drafted plan. Concurrent project edits are rejected rather than overwritten.
- **Contacts:** Searchable company and contact selectors, related contact/project/opportunity lists, contact counts, creation from relationship pickers and record notes. Contacts can remain unassigned when their company is unknown; projects and sales qualification still require an identified company. Selecting a different company clears the selected contact on an opportunity, intake or registration record.
- **Events and participation:** Event filters, an optional read-only Event column, and Event grouping in Companies and Contacts, with Event history inside contact/company records. List and Kanban grouping show a record once per linked event and retain an Unassigned group; event groups are derived from registrations and do not allow drag reassignment. Separate Events and Event participation tabs are hidden. Company filtering includes registrations linked directly to the company or to its contacts; contact filtering uses that person’s linked registrations. Registrations retain source details, attendance, sales-interest evidence and contact-matching status. Missing attendance stays Unknown. Marketing imports reuse clear contact identities, retain ambiguous matches for review and copy complete source snapshots. Only explicit contact-form, audit or consultation requests enter Lead intake automatically. Staff can also send a registration to intake with an idempotent action. Company/contact merges retain event relationships.
- **Marketing follow-up:** Accounts, Contacts and linked intake leads expose the same canonical registration fields: Marketing follow-up, separate follow-up/DC/marketing notes, first email sent, audit/consultation requests and other form answers. Choose an Event context to scope columns, search, grouping and filters; the selection saves per user. Match all conditions requires event and response-field conditions to match the same registration. Event-grouped list rows scope response cells to the group event. A cell with one response edits that response directly; multiple responses open Event history for an explicit choice. Marketing follow-up Kanban moves are enabled only for an unambiguous response; imported checkbox flags remain filters and columns. Standalone contact-form leads keep their own response metadata. Source checkboxes distinguish unchecked from unknown, and an email flag never implies attendance or sales interest. Original combined notes and raw snapshots remain intact. Source quantities/prices are retained as labelled metadata and never enter financial totals.
- **Services and vendor costs:** A service catalog under Projects, per-project service lines and external work orders. Service groups are defaults rather than restrictions. Vendor budgets and recorded actual amounts remain distinct.
- **Duplicate review:** Under Contacts. Suggestions can be searched, dismissed or reviewed side by side. The user chooses the surviving record; the existing audited merge RPC reassigns BizBase relationships and retains before-images. No automatic merge is performed.
- **Shared table controls:** Inline text/dropdown edits, double-click record dialogs, list and Kanban views, sorting, drag-and-drop column ordering, visible columns and pagination. Column headers have separate drag handles so sorting remains available; column order saves per user and survives hiding/showing fields. Owner filters offer the actual saved names. Every operational table supports field filters with a saved Match all / Match any choice for text, relationships, options, amounts, dates and empty values. List and Kanban offer curated business grouping choices (status/stage, owner, company, group, source, event and relevant classifications). Filters retain useful amount/date ranges and contact-completeness checks; titles, URLs, notes and display order are omitted from filter menus. Grouping excludes names, individual contact details, amounts, exact dates and document links. Product and label groupings show multi-value records in each relevant category without drag reassignment. List views have collapsible sections and counts; Kanban retains its own grouping. Saved views discard retired filter/group choices while retaining columns and sorting. Filters, groupings and layouts save per signed-in user in Supabase with a browser fallback. Hidden columns stay hidden across reloads. Kanban moves save only the grouping field and related stage probability; lead qualification outcomes use the review workflow.

Dialogs hide internal identifiers, provide named relationships, guard unsaved edits and support keyboard focus. All writes use business-field allowlists and require a returned row before reporting success. Versioned records use an optimistic concurrency check.

List and Kanban grouping menus omit fields with no assigned values in the current filtered/event view. A single real value (including No/false or zero) remains valid. If a saved grouping is empty in the current context, the list displays without grouping and Kanban uses an available field; the saved choice is retained for contexts where it has data. This does not hide columns or remove fields from record editors.

## Source data and boundaries

ClickUp and Pipedrive are strictly read-only. The frontend calls Supabase only; it has no source-system write credentials or outbound update path. Original source values, custom-field definitions, relationships, descriptions and source IDs remain in `migration_staging`. Merged source identities are resolved through `source_identity_map`.

Record cards no longer have an Imported fields tab (4 Nov 2026). The original ClickUp/Pipedrive snapshots stay in the database (`migration_staging`), and `loadSources` / `sourceFields` in `src/workspace-data.ts` can still render them with readable option labels. Original products, reported revenue range/channel and imported sales notes remain read-only source details. Editable opportunity labels/deal type retain their BizBase copies. Proposed services link to `services` through `opportunity_services`; exact source catalog matches are reused, other real source product labels retain explicit catalog entries. Quoted line amounts remain NULL when unknown. Delivery creation copies catalog identities, scope and quoted amounts without inventing prices.

`02 Projects` is outside the requested migration scope. Source import/parsing/promotion utilities and their tests remain in the repository; source-review and migration controls are not exposed as staff navigation screens. The legacy frontend is no longer part of the deployment.

Signed value, planned delivery revenue, issued invoices, cash collected, vendor budgets and recorded vendor actuals are separate measures. Imported working records can still require review, and held or excluded source records are not silently presented as validated operational data.

## Supabase

For a fresh project, run `supabase/setup.sql`. It combines all checked-in migrations in dependency order. For an existing project, apply only missing migrations from `supabase/migrations`.

Every new or recreated public table must declare explicit Data API grants in its creation migration, together with RLS and policies. Never depend on automatic grants, including on fresh projects, preview branches or database resets. Grant authenticated users only the required operations under staff RLS; CRM tables remain inaccessible to `anon`. Grant server roles explicitly when a server workflow needs them. Read-only projections receive SELECT only. Keep the combined setup script consistent with these migrations. See `AGENTS.md` for the development rules; the user's Supabase notice identifies October 30, 2026 as the end of automatic grants for new tables in existing projects.

Create staff accounts in Supabase Auth, disable public signup, and add active membership:

```sql
insert into public.workspace_members(user_id)
values ('<staff-user-uuid>');
```

The frontend checks membership and table policies enforce access. `user_preferences` stores each user's table layouts. `review_intake_lead` and `merge_bizbase_records` are the existing guarded workflows. The additional `create_delivery_project` and `save_project_revenue_plan` functions run with caller privileges and RLS; execution is denied to anonymous users.

The Pipedrive field-definition snapshot in `integration_events` provides authenticated labels for imported option values and owners. No CRM records are bundled into static assets.

## Cloudflare Pages

**Live app: https://bizbase.pages.dev** (production, deployed from `main`).

Project: `bizbase`, direct upload (not connected to GitHub, so pushing does not deploy). Build command: `npm run build`. Output directory: `dist`. Deploy from a clean build:

```sh
rm -rf dist && npm run build
npx wrangler pages deploy dist --project-name bizbase --branch main
```

The old preview alias `https://codex-cloudflare-frontend.bizbase.pages.dev` (branch `codex/cloudflare-frontend`) was updated to the same build on 4 November 2026. Use the live address above instead.

Preview URLs are public; Supabase staff authentication gates all CRM data. Production and preview currently use the same authenticated workspace, so normal UI writes affect the shared BizBase data. Use a separate Supabase project before testing destructive or speculative migrations.

Always clean the build output before deploying so obsolete legacy assets are not retained. The app has no service worker or offline CRM cache.
